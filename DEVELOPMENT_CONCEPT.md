# Концепция разработки (стандарт для всех проектов)

> Этот файл кладётся в корень каждого проекта как `CLAUDE.md` (или `docs/DEVELOPMENT_CONCEPT.md`)
> и является обязательным вводным требованием при любой разработке.

## 1. Версионирование
- Формат SemVer: `MAJOR.MINOR.PATCH`, первая версия — **1.0.0**.
- Мелкие обновления/исправления → третья цифра (`1.0.0 → 1.0.1`).
- Крупные обновления/новый функционал → вторая цифра (`1.0.5 → 1.1.0`).
- Первая цифра — только при несовместимых изменениях архитектуры/API.
- Версия хранится в одном месте в коде (`VERSION` / константа) и отображается в UI, API (`GET /api/v1/version`) и логах при старте.
- **Номер версии всегда отображается в меню проекта** (например, `vX.Y.Z` внизу бокового или в главном меню), на всех страницах и для всех ролей.
  По клику открывается окно «О программе»: версия, дата сборки, коммит, «Что нового», проверка обновлений.
  Если доступна новая версия — рядом с номером метка-индикатор (а для `security` — выделенная).
- В консольных утилитах — ключ `--version`, а номер версии выводится в шапке `--help`.

## 2. Центральный репозиторий обновлений `allupdsw`
- Публичный GitHub-репозиторий `allupdsw`; у каждого проекта — свой файл `<имя_проекта>.json`.
- У самого проекта — отдельный собственный репозиторий с кодом.
- Проект при старте и по расписанию (и по кнопке «Проверить обновления») читает:
  `https://raw.githubusercontent.com/lumenods/allupdsw/main/<имя_проекта>.json`
- Сравнивает с текущей версией, показывает номер новой версии, «Что нового» и **готовые команды обновления** для данного проекта.
- Проверка неблокирующая, с таймаутом и кэшем; отключаемая в настройках; ошибки сети пишутся в журнал, но не ломают работу.

Формат файла:
```json
{
  "project": "имя_проекта",
  "repository": "https://github.com/<owner>/<имя_проекта>",
  "latest": "1.1.0",
  "update_commands": {
    "linux": ["cd /opt/имя_проекта", "git pull", "./scripts/update.sh"],
    "docker": ["docker compose pull", "docker compose up -d"]
  },
  "versions": [
    {
      "version": "1.1.0",
      "date": "2026-11-15",
      "type": "minor",
      "changes": ["Новое: ...", "Улучшено: ..."],
      "breaking": false,
      "min_upgrade_from": "1.0.0"
    },
    {
      "version": "1.0.0",
      "date": "2026-10-31",
      "type": "initial",
      "changes": ["Первый релиз"]
    }
  ]
}
```

## 3. Архитектура и высокая нагрузка
- Проектируем сразу всю концепцию системы, а не только главный функционал: гибкость, расширяемость, удобство.
- Сразу закладываем высокую нагрузку: асинхронность/пулы, кэширование, индексы БД, пагинация, лимиты запросов, очереди для тяжёлых задач, горизонтальное масштабирование (stateless-сервисы).
- Тюнинг системы описывается в документации: параметры ОС (`sysctl`, `ulimit`), веб-сервера, БД, пулов соединений — с рекомендуемыми значениями.

## 4. API
- В каждом проекте сразу есть API (`/api/v1/...`), версионированное.
- Описание всех методов: OpenAPI/Swagger-спецификация + страница документации внутри системы (параметры, типы, примеры запросов/ответов, коды ошибок).
- Авторизация API по токенам с правами согласно ролям.

## 5. Интерфейс и формы
- Интерфейс не перегружен: разделение по **вкладкам** + режим **«Все сразу»**.
- У полей и опций — краткие пояснения (всплывающие подсказки `?`/tooltip).
- **Мобильная версия обязательна** во всех проектах (см. раздел 13).
- В формах тестируем все возможные значения параметров, граничные случаи, а также **совместимость и противоречивость опций** (взаимоисключающие опции блокируются/подсвечиваются с объяснением; валидация и на клиенте, и на сервере).

## 6. Аутентификация, пользователи, группы/роли
- Если есть аутентификация — сразу пользователи + группы/роли согласно назначению проекта.
- Пользователей и группы/роли можно **переименовывать** (связи хранятся по ID или неизменному коду, а не по имени).
- Права настраиваются на уровне ролей; есть администратор по умолчанию с обязательной сменой пароля.

### 6.1. Единый центр авторизации (Keycloak)
Пользователи всех проектов входят через **единый центр авторизации** — Keycloak на своём сервере
(OpenID Connect: authorization code + PKCE S256). Пароли, 2FA, блокировки, отключение сотрудника, LDAP/AD —
только в центре. Каждый проект — отдельный клиент центра; `client_id` = имя проекта в реестре `allupdsw`.

**Проект сам описывает свои роли и права, а назначаются они в центре:**
- Проект публикует **манифест прав**: `GET /api/v1/auth/manifest` (доступ — по сервисному токену центра).
  ```json
  {
    "system": "netmap", "version": "1.4.0", "manifest_version": 1,
    "permissions": [{"code": "map.view", "group": "Карта", "name": "Просмотр карты", "name_en": "View map"}],
    "roles": [{"code": "installer", "name": "Монтажник", "name_en": "Installer",
               "description": "…", "permissions": ["map.view", "node.view"], "deprecated": false}]
  }
  ```
- Центр забирает манифесты (синхронизация по расписанию и по кнопке) и заводит у клиента проекта
  **клиентские роли**: права — с префиксом `perm:` (`perm:map.view`), роли — составные из прав (`installer`).
- Состав роли из манифеста — это **значение по умолчанию** при её первом появлении. Дальше состав роли
  (какие права в неё входят) меняют администраторы **в центре**; синхронизация их правки не затирает,
  а только добавляет права, которые появились в манифесте впервые.
- **Должности** («Монтажник», «Инженер ЛКС», «Диспетчер») — группы центра, в которые входят роли разных
  проектов. Сотрудника включают в должность — он получает нужные роли во всех системах сразу.
  Роль конкретного проекта можно выдать и напрямую.
- Коды прав и ролей **не удаляются и не переименовываются**; переименовывается только название.
  Ставшее ненужным помечается `deprecated` — центр показывает его как «устарело», но не удаляет.

**Как проект получает права:**
- В `id_token` и `userinfo` — claim `resource_access.<client_id>.roles`: только роли и права **этого** проекта,
  составные роли уже раскрыты. Права — коды с `perm:`, роли — без префикса.
- Если в токене есть `perm:*` — действуют они. Если нет (центр ещё не настроен) — права берутся из ролей
  по составу из манифеста. Незнакомые коды игнорируются и не ломают вход.
- Ограничения **внутри** проекта (зоны и слои NetMap, «только свои заявки» и т. п.) задаются в самом проекте
  и накладываются поверх ролей из центра.
- Проект перепроверяет пользователя в центре по `refresh_token` не реже раза в 10 минут (настраивается):
  изменения ролей доходят без повторного входа, отключённого сотрудника проект выводит из системы.
  Поддерживается Back-Channel Logout — выход и «завершить сеансы» в центре сразу завершают сессии в проекте.
- Обмен данными между системами — сервисные учётные записи центра (`client_credentials`) с ролями проекта-получателя
  или собственные API-токены проекта.
- Запасной вход по паролю проекта при включённом центре — только для локального суперпользователя
  (на случай недоступности центра). Сессии, открытые до сбоя центра, продолжают работать до его возвращения.
- Пользователь в проекте связывается с центром по `sub` (неизменный ID центра), а не по логину.
- В справке проекта: список ролей и прав (из манифеста) и как подключить проект к центру.

## 7. Журналирование
- Журнал действий пользователей и системных событий (кто, что, когда, откуда, результат).
- Уровни: DEBUG / INFO / WARNING / ERROR.
- **Выгрузка журнала за точно указанный период** (дата+время «с»/«по», с секундами, с учётом часового пояса), фильтры по уровню/пользователю/типу; форматы CSV/JSON/TXT; также через API.
- Ротация и срок хранения логов настраиваются.

## 8. Отладка (debug) — закладывается всегда, с первой версии
- Режим отладки есть в **каждом** проекте; включается в настройках (администратором), переменной окружения
  (`<ПРОЕКТ>_DEBUG=1`) или ключом `--debug` — **без пересборки и, по возможности, без перезапуска**.
- Уровень детализации настраивается отдельно по модулям (например, `api=DEBUG, db=INFO`).
- Возможно временное включение («на 30 минут») с автоматическим выключением — чтобы не забыть debug на проде.
- Что пишется в debug: входящие/исходящие запросы (с маскировкой паролей и токенов), SQL-запросы и их время,
  обращения к внешним сервисам, время выполнения операций, полная трассировка ошибок.
- У каждого запроса — `request_id`, который виден пользователю в сообщении об ошибке и ищется в журнале.
- Страница «Диагностика» (только для администраторов): версия, время работы, состояние БД/кэша/очередей,
  нагрузка, конфигурация без секретов, кнопка «Скачать отчёт для отладки» (архив: версия, конфиг, логи за период).
- API: `GET /api/v1/debug/status`, `POST /api/v1/debug/level` — только для роли администратора.
- Индикатор в меню рядом с версией, когда включён режим отладки.
- Включение/выключение debug фиксируется в журнале (кто и когда).

## 9. Зависимости и лицензии
- Все фреймворки и библиотеки (JS/CSS/шрифты и т.п.) кладём **локально** в проект, без CDN.
- В документации — список всех используемых сторонних проектов, их версии, ссылки и **лицензии** (`THIRD_PARTY_LICENSES.md`).

## 10. Документация (справка)
Всегда подробная справка. **В документации описываются все функции системы без исключения**:
если функции нет в справке, она считается незавершённой (так же, как функция без тестов).

Для **каждой** функции в справке указывается:
- назначение: что делает и зачем;
- где находится: путь в меню или вкладке, на десктопе и в мобильной версии;
- все параметры и опции: тип, допустимые значения, значение по умолчанию, обязательность;
- ограничения: какие опции несовместимы или противоречат друг другу и что тогда происходит;
- кому доступна: роли и права;
- соответствующий метод API с примером запроса и ответа;
- пошаговый пример использования;
- возможные ошибки и сообщения, их причины и что делать;
- скриншоты: десктоп и мобильная версия.

Реестр функций `docs/FEATURES.md`: таблица «функция → раздел справки → API-метод → тесты».
Тест проверяет, что у каждой функции из реестра есть раздел справки и хотя бы один тест.

Справка обязательно включает:
- назначение и возможности системы;
- **архитектуру системы** (схема компонентов, потоки данных, БД, внешние связи);
- установку, обновление (в т.ч. из `allupdsw`), настройку и тюнинг;
- руководство пользователя и администратора (вкладки, опции, роли);
- описание API;
- журналирование, отладку, устранение неполадок;
- тестирование: как запустить и что покрыто;
- историю версий (CHANGELOG, синхронизирован с `allupdsw/<проект>.json`);
- сторонние компоненты и лицензии.

### Скриншоты
- Руководство пользователя и администратора иллюстрируется **скриншотами** каждого экрана, вкладки,
  важной формы и диалога (включая «О программе» с номером версии и окно обновления).
- Скриншоты **генерируются автоматически** e2e-тестами (Playwright) на демо-данных, а не снимаются вручную.
  Поэтому они всегда соответствуют текущей версии и пересоздаются одной командой (`make screenshots`).
- Отдельные наборы для каждого языка: `docs/screenshots/ru/`, `docs/screenshots/en/`.
  Если в интерфейсе есть тёмная тема, снимаем и её.
- Фиксированный размер окна (например, 1440×900) плюс мобильная ширина для ключевых экранов;
  важные элементы выделяются рамкой или стрелкой с номером, на который ссылается текст.
- На скриншотах нет реальных персональных данных, паролей и токенов, только демо-данные.

### PDF-документ
- Из той же справки собирается **PDF**: отдельный файл для каждого языка
  (`docs/pdf/<проект>-<версия>-ru.pdf`, `...-en.pdf`).
- Содержимое PDF: титульный лист (название, **номер версии**, дата сборки), оглавление с переходами по ссылкам,
  нумерация страниц, все разделы справки, включая архитектуру, API и скриншоты.
- Сборка одной командой (`make pdf`) из исходников справки (Markdown/HTML), например печатью
  через Playwright/Chromium или pandoc. Шрифты с кириллицей хранятся в проекте локально.
- PDF пересобирается при каждом релизе (в CI) и прикладывается к GitHub Release.
- PDF доступен из интерфейса: «Справка → Скачать PDF» на текущем языке пользователя.
- Справка в интерфейсе, Markdown в репозитории и PDF строятся из **одного источника**, без ручного дублирования текста.

### Проверка документации (входит в тесты)
- Скриншоты пересоздаются без ошибок, на каждый файл есть ссылка из текста, и в тексте нет ссылок на несуществующие файлы.
- PDF собирается на обоих языках, версия на титульном листе совпадает с `VERSION`.
- Все ссылки внутри справки рабочие.

## 11. Языки интерфейса и справки
- Во всех приложениях **язык по умолчанию — русский**, дополнительно — **английский**.
- Переключатель языка (RU / EN) в меню рядом с номером версии; выбор сохраняется в профиле пользователя
  (без авторизации — в cookie/локальных настройках). Язык по умолчанию для системы задаётся в настройках администратором.
- Все строки интерфейса — только через файлы локализации (`locales/ru.json`, `locales/en.json` или аналог фреймворка),
  никакого текста, «зашитого» в код. Ключи одинаковые в обоих языках; отсутствующий перевод → русский текст + запись в debug-журнал.
- Переводится всё: меню, вкладки, формы, всплывающие подсказки, сообщения валидации и ошибок, письма/уведомления, выгрузки (заголовки CSV).
- Справка в двух языках: `docs/ru/` и `docs/en/` (или README.md + README.en.md), структура разделов одинаковая, включая архитектуру.
- API: сообщения об ошибках на языке из заголовка `Accept-Language` (по умолчанию русский), коды ошибок — неизменные, не зависят от языка.
- Журнал: служебные события пишутся с кодом события; текст — на языке системы по умолчанию.
- Даты, числа и время форматируются по выбранному языку; в БД хранятся в UTC.
- «Что нового» в `allupdsw`: поле `changes` (русский) и `changes_en` (английский) — клиент показывает по языку пользователя,
  при отсутствии `changes_en` показывает `changes`.
- Тест: проверка, что ключи в `ru` и `en` совпадают (автотест/CI), и визуальная проверка, что длинные английские/русские строки не ломают вёрстку.

## 12. Тестирование — вся функциональность сразу
Тесты пишутся **одновременно с функционалом**, а не «потом». Функция без тестов считается незавершённой.

**Что покрывается обязательно:**
- **Модульные тесты** — вся бизнес-логика, включая граничные значения и ошибки.
- **API** — каждый метод: корректные данные, все параметры, неверные типы, пустые/огромные значения,
  отсутствие авторизации, доступ под **каждой ролью** (разрешено/запрещено), пагинация, коды ошибок, язык ответа (RU/EN).
- **Формы** — все параметры, граничные значения, **все сочетания опций** (как минимум попарные — pairwise),
  взаимоисключающие и противоречивые опции, валидация на клиенте и на сервере одинаковая.
- **Интерфейс (e2e, Playwright)** — **все** пользовательские сценарии (не только основные) на обоих языках,
  вкладки и режим «Все сразу», подсказки, номер версии в меню, переключение языка.
  Браузеры: Chromium, Firefox, WebKit (движок Safari, iOS).
- **Мобильная версия** — те же e2e-сценарии на эмуляции устройств (телефон 360×800 и 390×844, планшет 768×1024,
  портретная и альбомная ориентация, касания вместо мыши): нет горизонтальной прокрутки, элементы не перекрываются,
  меню, формы, таблицы и диалоги работают, номер версии виден, клавиатура не закрывает поле ввода.
- **Документация** — у каждой функции из `docs/FEATURES.md` есть раздел справки и тесты; скриншоты и PDF собираются.
- **Пользователи и роли** — создание, переименование пользователей и групп (связи не теряются), смена прав.
- **Журнал** — запись событий, выгрузка за период: точные границы «с/по» (включительно), часовые пояса,
  пустой период, очень большой период, все форматы выгрузки.
- **Проверка обновлений** — новая версия есть / нет / текущая новее реестра, нет сети, битый JSON, 404,
  `min_upgrade_from`, `breaking`/`security`, язык `changes_en` и запасной `changes`.
- **Debug** — включение/выключение без перезапуска, маскировка паролей и токенов в логах, `request_id`.
- **Локализация** — ключи `ru` и `en` совпадают, нет текста вне файлов перевода.
- **Обновление с предыдущей версии** — миграции БД на копии данных прошлой версии, откат.
- **Нагрузочные тесты** (k6 / locust) — целевые RPS и время ответа задаются в справке и проверяются перед релизом.
- **Безопасность** — SQL-инъекции, XSS, CSRF, перебор паролей, доступ к чужим данным.

**Правила:**
- Один запуск всех тестов одной командой (`make test` / `./scripts/test.sh`), он же запускается в CI на каждый push.
- Релиз невозможен, пока не проходят все тесты.
- Каждый найденный баг → сначала тест, который его воспроизводит, потом исправление (регрессионный тест).
- Тестовые данные и фикстуры лежат в репозитории; тесты не зависят от интернета и друг от друга.
- Покрытие кода измеряется; цель — не ниже 80% для бизнес-логики.
- Уровни тестов: модульные → интеграционные (с реальной БД в контейнере) → API → e2e (десктоп и мобильные) → нагрузочные.
  В CI запускаются все уровни; отчёт (результаты, покрытие, скриншоты упавших e2e) сохраняется как артефакт сборки.
- «Плавающие» (нестабильные) тесты не допускаются: такой тест исправляется сразу, его нельзя просто пропустить.
- Тесты проверяют результат (данные в БД, ответ API, видимый текст), а не только то, что «ошибки не было».
- В справке раздел «Тестирование»: как запустить, что покрыто, результаты нагрузочных тестов.

## 13. Мобильная версия — обязательно
- Каждый проект с интерфейсом работает на телефонах и планшетах. Это полноценная версия, а не урезанная:
  **все функции доступны и с мобильного**.
- Адаптивная вёрстка (mobile-first): одна кодовая база, контрольные ширины 360, 390, 768, 1024, 1440 px.
- Меню на мобильном сворачивается в «гамбургер» или нижнюю панель; **номер версии и переключатель языка видны и там**.
- Вкладки прокручиваются горизонтально или превращаются в выпадающий список; режим «Все сразу» показывается одной колонкой.
- Таблицы на узком экране превращаются в карточки или прокручиваются внутри своего блока; вся страница не прокручивается по горизонтали.
- Элементы для нажатия не меньше 44×44 px, подсказки открываются по касанию (не только по наведению мыши).
- Поля ввода используют подходящую клавиатуру (`type="email"`, `tel`, `number`, `inputmode`), размер шрифта не меньше 16 px
  (чтобы iOS не увеличивал страницу).
- Учитываются вырезы экрана (`safe-area-inset`), тёмная тема системы, медленный мобильный интернет (лёгкие страницы, сжатие, ленивая загрузка).
- По возможности PWA: иконка на главный экран, работа при кратковременной потере сети.
- В справке отдельный раздел «Мобильная версия» со скриншотами.
